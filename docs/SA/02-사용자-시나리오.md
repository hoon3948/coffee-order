## 4. 핵심 사용 시나리오

### 시나리오 #1: 신규 사용자 회원가입 및 첫 주문

**배경**: 김민수는 처음으로 커피숍 앱을 사용합니다.

**사용자 목표**: 회원가입 후 커피를 주문하고 싶다.

**사전 조건**: 
- 앱이 설치되어 있음
- 인터넷 연결 가능

**시나리오 흐름**:

1. **회원가입**
   - 앱 실행 → "회원가입" 버튼 클릭
   - 이메일, 비밀번호, 이름 입력
   - "가입 완료" 버튼 클릭
   - ✅ **성공**: JWT Access Token + Refresh Token 발급

2. **포인트 충전**
   - 메인 화면에서 "포인트 충전" 버튼 클릭
   - 충전 금액 선택 (5,000원 / 10,000원 / 30,000원)
   - "충전하기" 버튼 클릭
   - ✅ **성공**: 포인트 잔액 업데이트

3. **메뉴 조회**
   - 메인 화면에서 "메뉴 보기" 버튼 클릭
   - 전체 메뉴 목록 조회
   - 인기 메뉴 3개가 상단에 표시됨

4. **주문 및 결제**
   - 원하는 메뉴 선택 (예: 아메리카노 4,500원)
   - "주문하기" 버튼 클릭
   - 포인트 차감 확인 팝업 → "확인" 클릭
   - ✅ **성공**: 주문 완료, 포인트 차감

5. **주문 확인**
   - 주문 완료 화면에서 주문 번호 확인
   - 푸시 알림으로 주문 상태 수신

**예상 소요 시간**: 3~5분

**성공 기준**:
- 회원가입 성공률 > 95%
- 첫 주문 완료율 > 80%
- 평균 주문 시간 < 2분

---

### 시나리오 #2: 기존 사용자 빠른 주문

**배경**: 이지은은 이미 앱을 사용해본 경험이 있습니다.

**사용자 목표**: 빠르게 인기 메뉴를 주문하고 싶다.

**사전 조건**:
- 이미 로그인되어 있음 (JWT 자동 갱신)
- 포인트 잔액 충분 (10,000P)

**시나리오 흐름**:

1. **앱 실행**
   - 앱 아이콘 클릭
   - ✅ **자동 로그인**: JWT 토큰 검증 성공

2. **인기 메뉴 확인**
   - 메인 화면에 인기 메뉴 3개 자동 표시
   - 1위: 아메리카노 (4,500원)
   - 2위: 카페라떼 (5,000원)
   - 3위: 바닐라라떼 (5,500원)

3. **주문**
   - 인기 메뉴 1위 "아메리카노" 클릭
   - "주문하기" 버튼 클릭
   - ✅ **성공**: 주문 완료 (1초 이내)

4. **확인**
   - 주문 완료 화면 표시
   - 잔여 포인트: 5,500P

**예상 소요 시간**: 30초 이내

**성공 기준**:
- 주문 완료 시간 < 1분
- 인기 메뉴 클릭률 > 60%

---

### 시나리오 #3: 동시 주문 상황 (동시성 테스트)

**배경**: 점심시간에 100명의 사용자가 동시에 같은 메뉴를 주문합니다.

**사용자 목표**: 모든 사용자가 정상적으로 주문을 완료하고 싶다.

**사전 조건**:
- 100명의 사용자가 모두 로그인되어 있음
- 각 사용자의 포인트 잔액: 10,000P
- 주문 메뉴: 아메리카노 (4,500원)

**시나리오 흐름**:

1. **동시 주문 시작**
   - 100명이 동시에 "주문하기" 버튼 클릭
   - 서버에 100개의 주문 요청 동시 도착

2. **동시성 제어**
   - Redis 분산 락으로 사용자별 포인트 차감 순차 처리
   - MySQL 비관적 락으로 포인트 조회 시 행 잠금
   - ✅ **성공**: 모든 사용자의 포인트가 정확히 4,500P 차감됨

3. **결과 확인**
   - 100명 모두 주문 성공
   - 포인트 마이너스 발생 0건
   - 주문 집계 정확도 100%

**예상 소요 시간**: 10~30초 (동시 처리)

**성공 기준**:
- 포인트 정합성 100%
- 주문 실패율 0%
- 평균 응답 시간 < 500ms

### 시나리오 #4: 외부 API 장애 상황

**배경**: 주문 데이터를 전송하는 외부 API가 일시적으로 장애 상태입니다.

**사용자 목표**: 외부 API 장애와 무관하게 주문을 완료하고 싶다.

**사전 조건**:
- 사용자가 로그인되어 있음
- 포인트 잔액 충분
- 외부 API가 응답하지 않음 (타임아웃)

**시나리오 흐름**:

1. **주문 시도**
   - 사용자가 "주문하기" 버튼 클릭
   - 포인트 차감 + 주문 생성 성공
   - Kafka 이벤트 발행 성공

2. **외부 전송 실패**
   - Kafka Consumer가 외부 API 호출 시도
   - 외부 API 타임아웃 (3초)
   - ❌ **실패**: 첫 번째 전송 실패

3. **재시도**
   - Kafka Consumer가 자동 재시도 (최대 3회)
   - 2번째 시도: 실패
   - 3번째 시도: 실패
   - → Dead Letter Queue (DLQ)로 이동

4. **사용자 경험**
   - ✅ **주문은 성공**: 사용자는 주문 완료 화면 확인
   - 포인트 정상 차감
   - 주문 내역 저장됨

5. **복구 후 처리**
   - 외부 API 복구 후 DLQ에서 재처리
   - 최종적으로 외부 플랫폼에 데이터 전송 성공

**예상 소요 시간**: 주문 완료 < 1초, 외부 전송 최종 성공 < 10분

**성공 기준**:
- 주문 성공률 100% (외부 API 장애와 무관)
- 최종 전송 성공률 99% 이상
- 사용자는 외부 API 장애를 인지하지 못함

## 5. 엣지 케이스 (Edge Cases)

### 5.1 포인트 부족 시나리오

**상황**: 사용자가 주문하려는 메뉴 가격보다 포인트가 부족함

**시나리오**:
1. 사용자가 5,000원짜리 메뉴 선택
2. 현재 포인트 잔액: 3,000P
3. "주문하기" 버튼 클릭
4. ❌ **실패**: "포인트가 부족합니다" 에러 메시지
5. "포인트 충전하기" 버튼 표시
6. 사용자가 충전 후 재주문

**기대 동작**:
- 주문 전 포인트 잔액 검증
- 명확한 에러 메시지 표시
- 충전 페이지로 즉시 이동 가능

---

### 5.2 JWT 토큰 만료 시나리오

**상황**: Access Token이 만료되었지만 Refresh Token은 유효함

**시나리오**:
1. 사용자가 1시간 이상 앱을 사용하지 않음
2. Access Token 만료 (1시간)
3. 사용자가 앱 재실행
4. ✅ **자동 갱신**: Refresh Token으로 새 Access Token 발급
5. 사용자는 재로그인 없이 계속 사용

**기대 동작**:
- 자동 토큰 갱신 (사용자 인지 불가)
- Refresh Token도 만료 시 로그인 화면으로 이동

---

### 5.3 네트워크 끊김 시나리오

**상황**: 주문 중 네트워크 연결이 끊김

**시나리오**:
1. 사용자가 "주문하기" 버튼 클릭
2. 네트워크 요청 중 연결 끊김
3. ❌ **실패**: "네트워크 오류" 메시지
4. 사용자가 네트워크 복구 후 재시도
5. ✅ **성공**: 주문 완료

**기대 동작**:
- 명확한 에러 메시지
- 재시도 버튼 제공
- 중복 주문 방지 (멱등성 보장)
