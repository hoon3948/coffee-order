## 2. 프로젝트 목적

### 2.1 비즈니스 목적
- 다수 서버 환경에서도 **안정적으로 동작**하는 커피숍 주문 시스템 구현
- 실무 환경에서 발생하는 **동시성 이슈**, **데이터 일관성** 문제 해결 능력 검증
- 확장 가능한 아키텍처 설계 및 구현 역량 증명

### 2.2 기술적 목적
- **동시성 제어**: 다중 인스턴스 환경에서 포인트 차감 시 race condition 방지
- **데이터 일관성**: 포인트 잔액이 절대 마이너스가 되지 않도록 보장
- **실시간 집계**: 주문 데이터를 기반으로 정확한 인기 메뉴 제공
- **외부 연동**: 주문 데이터를 외부 플랫폼으로 실시간 전송

## 5. 핵심 제약사항 및 해결 전략

### 5.1 동시성 제어
**문제**: 여러 사용자가 동시에 주문 시 포인트 차감 race condition 발생 가능

**해결 전략**:
- **비관적 락 (Pessimistic Lock)** 사용
- MySQL `SELECT ... FOR UPDATE`로 포인트 조회 시 행 잠금
- Redis Redisson 분산 락으로 다중 인스턴스 간 동기화

**Trade-off**:
| 방식 | 장점 | 단점 | 선택 이유 |
|------|------|------|-----------|
| 비관적 락 | 강한 일관성 보장 | 처리량 감소 | ✅ 포인트 마이너스 절대 불가 요구사항 |
| 낙관적 락 | 높은 처리량 | 충돌 시 재시도 필요 | ❌ 사용자 경험 저하 |

---

### 5.2 데이터 일관성 & 이벤트 기반 아키텍처
**문제**: 주문 생성 + 포인트 차감 + 외부 전송이 안정적으로 처리되어야 함

**해결 전략**:
- **트랜잭션 범위**: 포인트 차감 + 주문 생성 + Kafka 이벤트 발행
- **외부 전송**: Kafka Consumer가 비동기로 처리 (재시도 가능)
- **트랜잭션 격리 수준**: `READ_COMMITTED` (성능과 일관성 균형)
- **Transactional Outbox Pattern**: Kafka 발행 실패 시에도 이벤트 유실 방지

**아키텍처**:
```
[주문 API]
  ↓
[트랜잭션 시작]
  ├─ 포인트 차감 (비관적 락)
  ├─ 주문 생성
  └─ Kafka 이벤트 발행 (order-created)
[트랜잭션 커밋] ← 여기까지만 동기 처리
  ↓
[Kafka Topic: order-events]
  ↓
[Consumer] → 외부 API 전송 (비동기)
  ├─ 성공: ACK
  └─ 실패: 재시도 (최대 3회) → DLQ
```

**근거**:
- Q3-B 선택: 주문은 성공, 전송은 비동기 재시도 (이벤트 기반)
- 외부 시스템 장애가 주문 실패로 이어지지 않음 (높은 가용성)
- 최종 일관성 (Eventual Consistency) 보장

**Trade-off**:
| 항목 | 동기 전송 (Q3-A) | Kafka 비동기 (Q3-B) | 선택 |
|------|------------------|---------------------|------|
| 트랜잭션 시간 | 500ms~2s | 10ms 이하 | ✅ |
| 가용성 | 외부 API 장애 시 주문 실패 | 주문 성공, 전송 재시도 | ✅ |
| 일관성 | 강한 일관성 | 최종 일관성 | ⚠️ |
| 복잡도 | 낮음 | 높음 | ⚠️ |
| 처리량 | 외부 API 속도 제한 | 독립적 확장 | ✅ |

### 5.3 인기 메뉴 집계
**문제**: "최근 7일간" + "정확한 주문 횟수" 요구사항

**해결 전략**:
- **실시간 집계 테이블** 사용 (`menu_statistics`)
- 주문 생성 시 트랜잭션 내에서 집계 테이블 업데이트
- Redis 캐싱으로 조회 성능 개선 (TTL 5분)

**구조**:
```sql
CREATE TABLE menu_statistics (
    menu_id BIGINT,
    order_date DATE,
    order_count INT,
    PRIMARY KEY (menu_id, order_date)
);
```

**Trade-off**:
| 방식 | 정확성 | 성능 | 복잡도 | 선택 |
|------|--------|------|--------|------|
| 실시간 집계 | ⭐⭐⭐ | ⭐⭐ | ⭐⭐ | ✅ |
| 배치 집계 | ⭐⭐ | ⭐⭐⭐ | ⭐ | ❌ |
| Redis Sorted Set | ⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐ | ❌ |

### 5.4 다중 서버 환경
**문제**: 여러 인스턴스가 동시에 같은 사용자의 포인트를 차감할 수 있음

**해결 전략**:
- **Redis 분산 락** (Redisson)
- 락 키: `lock:user:{userId}:point`
- 락 획득 실패 시 재시도 (최대 3초 대기)

**인프라 구성**:
```
[Client] 
   ↓
[Nginx Load Balancer]
   ↓
[App Instance 1] [App Instance 2] [App Instance 3]
   ↓                ↓                ↓
[MySQL Master] ← [Redis Cluster] → [Kafka Cluster]
                                         ↓
                                    [Consumer Group]
                                         ↓
                                    [External API]
```

### 5.5 사용자 인증/인가
**문제**: 사용자 식별 및 API 접근 제어 필요

**해결 전략**:
- **JWT (JSON Web Token)** 기반 무상태 인증
- Spring Security + JWT Filter Chain
- Access Token (유효기간 1시간) + Refresh Token (유효기간 7일)

**인증 흐름**:
```
[회원가입/로그인]
  ↓
[JWT 발급] (Access Token + Refresh Token)
  ↓
[클라이언트] → Authorization: Bearer {token}
  ↓
[JWT Filter] → 토큰 검증 → SecurityContext 설정
  ↓
[API 접근 허용]
```

**보안 요구사항**:
- 비밀번호: BCrypt 해싱 (strength 10)
- JWT Secret: 환경변수로 관리 (최소 256bit)
- Refresh Token: Redis에 저장 (자동 만료)

**Trade-off**:
| 방식 | 장점 | 단점 | 선택 |
|------|------|------|------|
| JWT | 무상태, 확장성 좋음 | 토큰 무효화 어려움 | ✅ |
| Session | 즉시 무효화 가능 | 서버 메모리 사용, 확장성 낮음 | ❌ |
| OAuth 2.0 | 표준, 소셜 로그인 | 복잡도 높음 | ❌ |
